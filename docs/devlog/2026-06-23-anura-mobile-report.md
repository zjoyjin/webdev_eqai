# Anura 移动端调试与产品状态报告

## 背景

本轮工作的核心目标，是让 Anura 在手机浏览器上完成从打开摄像头、识别人脸、开始采集、上传分析到展示结果的完整体验。

项目的产品定位保持不变：参考 demo 的顺畅流程，但保留当前项目前后端拆分、密钥不暴露、数据更私密的架构优势。

## 当前进展

移动端基础链路已经明显推进。手机端现在可以通过 `HTTPS` 本地地址打开页面，前置摄像头可以启动，人脸检测框已经从早期的固定不动、无法识别人脸，推进到可以动态跟随人脸。

摄像头选择也从一堆无意义的编号设备，调整为更符合用户理解的前置摄像头、后置摄像头和真实外接摄像头。

准备阶段和正式采集阶段已经重新区分。之前准备阶段的进度条会自己跑到 `30` 秒，容易让用户误以为已经完成采集；现在已修正为：准备阶段只做人脸检测和画面质量判断，只有用户点击开始测量后才进入正式采集计时。

## 通俗解释

这次移动端问题看起来像一个摄像头问题，实际是几条链路叠在一起。

第一层是手机浏览器能不能安全打开摄像头。手机浏览器对摄像头权限更严格，必须在可信的 `HTTPS` 页面里运行。页面能在电脑上打开，不代表手机上就能顺利调用摄像头。

第二层是手机到底打开了哪个摄像头。手机通常有前置、后置、广角等多个摄像头，浏览器返回的设备名称有时不准确，甚至只给编号。用户看到一堆 `0` 到 `5` 的摄像头时，很难知道自己到底选了什么。

第三层是摄像头画面能不能被算法正确读取。摄像头打开只是第一步，页面还要持续拿到清晰的视频帧，并把视频帧送给人脸检测算法。手机上经常会出现视频尺寸刚开始很小、画布尺寸不同步、画面方向和显示比例不一致等问题。

第四层是人脸框能不能真正跟着脸走。页面上看到一个框，不代表算法真的在实时识别人脸。之前出现过绿框固定不动的情况，本质上是 `UI` 显示和实际检测结果没有同步。现在已经把检测结果、画面尺寸和框的位置重新对应起来。

第五层是准备完成不等于采集完成。准备阶段只是在确认摄像头、人脸位置、画面质量和信噪比；正式采集需要用户点击开始后，连续采集 `30` 秒，并把数据分成 `6` 段上传分析。

第六层是采集完成不等于结果已经显示。采集结束后，服务端还要完成后运算，前端还要轮询结果并把结果展示给用户。所以“`30` 秒走完”“服务端收到 `6` 段数据”“页面展示最终结果”是三个不同节点，必须逐个对齐。

## 产品价值变化

这次调试让产品从桌面端可用、手机端不稳定，推进到手机端核心交互基本成立。

这对 Anura 很重要，因为生命体征检测天然更适合手机前置摄像头场景。移动端体验是否成立，直接决定产品能不能被普通用户自然使用。

同时，项目没有回退到 demo 那种把能力都压在前端里的方式，而是保留了服务端承接真实配置和结果处理的方式。这一点对后续隐私、安全和商业化接入更友好。

## 主要问题演进

| 阶段 | 用户看到的问题 | 当前处理结果 |
| :-- | :-- | :-- |
| 访问阶段 | 手机打不开、503、空响应、证书异常 | 已改为 HTTPS 局域网访问方式 |
| 摄像头阶段 | 手机只开后置、切换无效、设备列表混乱 | 已优化默认前置和设备命名 |
| 人脸检测阶段 | 红框或绿框固定不动，检测不到人脸 | 已推进到动态跟随人脸 |
| 准备阶段 | 没点开始也像在采集 | 已修正，准备阶段进度不再自动走 |
| 采集阶段 | 采集结束后结果没对应上 | 已发现一次完整 `6` 段采集完成记录，前端展示链路仍需继续确认 |

## 当前产品状态

移动端已经具备进入真实测试的基础条件：摄像头能开、人脸能跟踪、画面质量和信噪比判断可用，真实 DeepAffex 配置已接入，并且已有一次完整 `6` 段采集完成记录。

但还不能说移动端体验已经完全闭环。当前关键点是用户完成 `30` 秒采集后，结果是否及时、明确、稳定地展示出来。这一步决定用户是否相信检测已经完成，也决定产品体验是否像 demo 一样顺滑。

## 结论

本轮工作把 Anura 移动端从摄像头和人脸检测不可用，推进到核心检测链路基本可跑。

当前产品重点已经从底层连通，转向结果展示和完整体验闭环。
